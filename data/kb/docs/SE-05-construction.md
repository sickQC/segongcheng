## 软件构造活动的范围

软件构造（software construction）是指通过编码、验证、单元测试、集成测试与调试的组合，详细地创造出可运行软件的活动。它是把需求与设计转化为可执行制品的过程，也是项目中产生配置项（源文件、测试用例、构建脚本）数量最多的活动。

按照 SWEBOK 的划分，软件构造知识域包含构造基础（最小化复杂度、预见变化、面向验证的构造、复用、构造中的标准）、构造管理（构造计划与度量）、实践考虑（构造设计、编码、构造测试、构造质量、集成）以及构造技术（API 设计、断言与契约式设计、错误与异常处理、测试先行编程等）。SWEBOK V4.0（2024 年）新增了管理依赖、领域特定语言、微服务、DevOps 与持续交付、云开发环境、低代码/零代码等主题。

构造的边界随生命周期模型而变：瀑布等线性模型把构造放在需求与设计之后，主要表现为编码；敏捷模型让构造与需求、设计、测试并行发生。无论采用何种模型，构造都包含构造计划、详细设计、单元测试与集成测试，而不仅是写代码。

## 构造中的设计

构造阶段必然包含设计。SWEBOK 的表述是：正如建造实体建筑时需根据图纸中未预料到的缝隙做小尺度调整，构造者也要在构造中补齐设计细节，其内容与软件设计相同，但尺度更小——集中在算法、数据结构与接口层面。

构造设计遵循三条原则：**信息隐藏**（只暴露稳定接口，封装易变细节）、**高内聚低耦合**（单一职责、依赖少且单向）、**为变化留出接缝**（把可能变化的策略抽成参数、接口或配置）。

## 编码规范与代码风格

编码规范（coding standard）是对命名、布局、缩进、注释、语言子集等做出统一约定的组织级或项目级规则。SWEBOK 把"构造中的标准"列为构造基础之一，并指出标准直接作用于编码风格、编程语言与平台接口。

代码风格（code style）是编码规范中关于可读性的部分。风格不改语义，但显著影响维护成本：一致风格让读者关注逻辑而非形式，也让审查与静态分析更易自动化。

### 命名与注释

命名的三条实用规则：**名实相符**（名字描述"是什么"而非"怎么做"）、**长度与作用域匹配**、**避免魔法值**（用命名常量代替裸字面量）。

注释应解释"为什么"而非复述"做什么"，其价值在于记录意图、约束与权衡；过时的注释比没有注释更危险，改代码必须同步改注释。

## 防御式编程、断言与契约式设计

防御式编程（defensive programming）是指保护例程不被非法输入破坏的做法，常见手段是检查全部输入参数并决定如何处理坏输入。断言（assertion）是放在程序中的可执行谓词，用于运行时检查程序状态；它通常在开发期编译进代码、发布时移除以免影响性能。

契约式设计（design by contract）是一种为每个例程规定前置条件与后置条件的开发方法；当前置、后置条件被使用时，每个例程或类都与程序其余部分形成一份"契约"。契约同时是例程语义的精确说明，有助于理解其行为。

三者的分工可用一条边界说清：**前置条件是调用方的义务**（可用断言检查），**后置条件是实现方的义务**（应由单元测试验证），**输入校验属于对不可信边界的防御**（面向用户输入，发布版中必须保留）。

### 错误处理与异常设计

SWEBOK 列出的常见错误处理手段包括：返回中立值、替换为下一条有效数据、记录警告日志、返回错误码、直接关闭软件；异常通过 throw 抛出、由 try-catch 块捕获。

异常设计的工程原则包括：异常消息包含全部关键信息；避免空 catch 块；了解所调用库会抛出哪些异常；建立集中式异常上报；统一项目内的异常风格。常见判据是"异常只用于真正的异常"：可预期的业务结果（如"用户名已存在"）应作为返回值处理。

## 代码复用与 API 设计

复用（reuse）是指用已有资产解决不同问题，典型资产包括库、模块、组件、源代码与商业现成（COTS）产品。SWEBOK 区分"构造以复用"（创造可复用资产）与"复用而构造"（把已有资产集成进新系统），系统性复用能显著改善生产率、质量与成本。

API（application programming interface）是库或框架导出给使用者的签名集合；SWEBOK 强调 API 除签名之外还必须说明其效果与行为语义。优秀 API 应易于学习记忆、使调用代码可读、难以被误用、易于扩展、完整并保持向后兼容。

## 代码审查与结对编程

代码审查（code review）是由代码作者以外的人检查该段代码的过程。Google 工程实践文档把审查关注点归纳为八项：设计、功能、复杂度、测试、命名、注释、风格、文档；并指出若作者与他人结对编程且对方有资格做出良好评审，该代码即视为已被审查。

代码审查的步骤：

1. 作者提交小而完整、可独立理解的变更，并说明意图。
2. 审查者先理解设计与意图，再逐项检查上述八项。
3. 区分"必须修改"与"可选建议"，不把个人偏好当作阻塞项。
4. 作者逐条修改，或说明理由并达成一致。
5. 合并后把反复出现的问题沉淀为规范或自动检查规则。

结对编程（pair programming）由两人共用一台机器，分别承担"驾驶员"（写代码）与"领航员"（审视方向与缺陷）角色并频繁轮换，把审查前移到编码过程中，代价是即时的人力投入。

## 静态分析与代码质量度量

静态测试是不执行被测软件而对其工作产品进行评价的活动，手段包括人工评审与工具化的静态分析（static analysis）。ISTQB 基础级大纲指出：静态分析常在动态测试之前发现缺陷，且因不需要测试用例而工作量更小；它还能发现动态测试无法发现的缺陷（如不可达代码），被广泛用于评估可维护性与安全性，并常集成进持续集成框架。

### 圈复杂度

圈复杂度（cyclomatic complexity）由 McCabe 于 1976 年提出，用于度量程序控制流的复杂程度。对控制流图 G，V(G) = E − N + 2p，其中 E 为边数、N 为节点数、p 为连通分量数（单一连通程序 p = 1）；实践中更常用的等价算法是：圈复杂度 = 判定点数量 + 1，判定点包括 if、while、for、case 分支及布尔表达式中的 && 与 ||。

例如下面这段 Java 代码：

```java
int grade(int score) {
    if (score < 0 || score > 100) return -1;   // 判定点 2 个（<0、>100）
    if (score >= 90) return 4;                 // 判定点 1 个
    else if (score >= 60) return 2;            // 判定点 1 个
    else return 0;
}
```

其圈复杂度为 2 + 1 + 1 + 1 = 5。圈复杂度等于独立路径数，因此给出了达到基本路径覆盖所需测试用例的下界；团队通常设定阈值（如单函数不超过 10），超过即提示重构。

### 重复率

重复率（code duplication ratio）通常定义为被检测为重复的代码行数占总代码行数的比例，重复片段常称为代码克隆（code clone）。克隆会带来"改一处漏一处"的风险。但重复率不是越低越好：判断标准应是"两段代码是否因同一原因而变化"。

## 重构手法

重构（refactoring）是在不改变代码外部可观察行为的前提下改进其内部结构的过程。Martin Fowler 的重构目录给出系统化手法，常用者可分为提炼类（Extract Function/Class/Variable）、搬移特性（Move Function/Field）、组织数据（Encapsulate Variable）、简化条件逻辑（Decompose Conditional、Replace Nested Conditional with Guard Clauses）与重构 API（Change Function Declaration）等类别。

重构的安全步骤：

1. 确认存在覆盖待改代码的自动化单元测试，且全部通过。
2. 选择一个小手法，一次只做一件事。
3. 执行手法并运行测试；失败则先回退，而不是继续叠加改动。
4. 测试全绿后提交，保持每次提交都是可工作的版本。
5. 结构改善完成后再加入新功能，避免重构与改行为混在同一次提交。

**重构与重写的区别**：重构保持行为不变、小步前进、可随时停止；重写改变行为与结构，风险更高。

## 构建与依赖管理

构建（build）是把源代码、资源与依赖转换为可运行制品的过程，通常包括编译、链接、打包、测试与制品发布；现代实践把构建脚本纳入版本控制，并在持续集成中每次提交都执行一次完整构建。

依赖管理（dependency management）处理第三方库的引入、版本选择与冲突消解。语义化版本（SemVer 2.0.0）规定版本号形如 MAJOR.MINOR.PATCH：不兼容的 API 变更递增 MAJOR，向后兼容地新增功能递增 MINOR，向后兼容的缺陷修复递增 PATCH。依赖声明过紧会导致版本锁定，过松会假设超出合理范围的兼容性，因此需要配合锁定文件与自动化升级策略。

## 常见误解与易混淆概念

**❌ 错误理解：软件构造就是"写代码"。**
✅ 正确理解：构造是编码、详细设计、单元测试、集成测试与调试的组合，还包括构造计划、复用决策与质量活动。
**辨析**：SWEBOK 把构造定义为"详细地创造出可运行软件"，它同时依赖设计输出并向测试提供输入。

**❌ 错误理解：断言可以替代输入校验，发布版里留着断言更安全。**
✅ 正确理解：断言面向"不应发生"的编程错误，通常在发布版中被编译移除；面向不可信输入的校验必须保留。
**辨析**：断言检查程序内部一致性（如不变量），失败说明代码有缺陷；输入校验检查外部世界的不可信数据，失败是正常业务分支。

**❌ 错误理解：防御式编程与契约式设计是同一件事。**
✅ 正确理解：契约式设计把前置条件规定为调用方的义务，实现方可以不检查；防御式编程要求例程主动检查输入以保护自己。
**辨析**：两者哲学相反——契约把责任写清楚，防御把责任揽过来。工程上常见做法是：对外部边界防御，对内部受控调用使用契约与断言。

**❌ 错误理解：异常处理就是给每段代码包一层 try-catch，catch 里打印日志即可。**
✅ 正确理解：异常只应处理当前层有能力处理的错误，无法处理的应向上传播；空 catch 是最危险的模式。
**辨析**：关键不在于"有没有 catch"，而在于"异常到达这一层时，这一层是否知道该做什么"。

**❌ 错误理解：圈复杂度越低越好，应该把所有 if 都拆掉。**
✅ 正确理解：圈复杂度是提示重构的信号，不是绝对指标；过度拆分会产生大量浅封装，增加跳转成本与耦合。
**辨析**：圈复杂度度量独立路径数，与可测试性强相关，但函数行数、参数个数与嵌套深度也需一并考虑；阈值用于触发讨论，而非自动判定质量。

## 与其他知识域的关系

**先修知识域**：软件需求（构造的输入是需求与验收标准）、软件设计（构造中的设计是其细化延续）、计算基础（数据结构、算法、编程语言语义）、软件配置管理（源代码、构建脚本与依赖清单都是配置项）。

**后续与并行知识域**：

- **软件测试**：单元测试与集成测试既是构造活动也是测试活动；测试为重构提供安全网。
- **软件维护**：重构、代码审查与静态分析是维护阶段控制技术债的主要手段。
- **软件质量**：ISO/IEC 25010 产品质量模型把可维护性、可靠性与安全性作为质量特性，编码规范、静态分析与审查是达成这些特性的构造层手段。
- **软件工程管理**：构造度量（代码量、复杂度、审查统计、缺陷发现率）是估算与过程改进的数据来源。
- **软件安全**：缓冲区溢出、越界访问等漏洞多在编码阶段引入，构造是安全左移的关键环节。
